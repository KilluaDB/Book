\section{Backend System Design}

The backend architecture is fundamentally divided into a control plane and a data plane. The control plane operates as the orchestration layer: it exposes the public API, authenticates users, stores platform metadata, and drives the state machine for project lifecycle management. The data plane encapsulates the provisioned tenant database instances, connection routing infrastructure, and the execution paths for queries and backups. This strict separation isolates orchestration logic from tenant workload execution, ensuring that control plane failures do not interrupt active database connections and allowing each plane to scale according to its distinct resource demands.

\subsection{Core Architectural Components}

To realize the separation of concerns between the control plane and the data plane, the system architecture comprises several specialized, highly cohesive components:

\begin{itemize}
    \item \textbf{Ingress and API Gateway (Traefik)}: Acts as the primary entry point for all external traffic. It handles TLS termination, path-based HTTP routing for the platform API, and TCP/SNI passthrough for direct tenant database connections.
    \item \textbf{Control Plane API \& Orchestration Worker}: The core backend is split. The API handles synchronous client requests (e.g., authentication, metadata retrieval), while a decoupled orchestration worker consumes asynchronous tasks from a message queue to interact with the Kubernetes API for infrastructure provisioning.
    \item \textbf{Meta-Database (PostgreSQL) \& Cache (Redis)}: PostgreSQL serves as the persistent source of truth for platform metadata (users, project state, billing tiers), while Redis operates as both a high-throughput message broker for the async workers and a low-latency cache for dynamic connection pooling.
    \item \textbf{Kubernetes Operators}: The platform relies on the \texttt{CloudNativePG} and \texttt{MongoDB Community} operators to declaratively translate high-level database topologies (e.g., replica sets, storage claims) into low-level Kubernetes primitives (Pods, StatefulSets, PVCs). Additionally, \texttt{cert-manager} is utilized to automate TLS certificate provisioning.
    \item \textbf{Data Plane Workloads}: This layer houses the isolated tenant namespaces. Each namespace encapsulates the underlying database engine alongside localized sidecars or proxy services, such as \texttt{PostgREST}, which provides automatic REST API generation on top of tenant schemas.
    \item \textbf{Observability Stack}: A centralized monitoring namespace running Prometheus (for metric scraping), Loki (for log aggregation), and Grafana (for visualization), ensuring comprehensive visibility into both control plane health and tenant database performance.
\end{itemize}

\subsection{Control Plane Architecture}

The control plane is designed around a multi-tiered architecture that explicitly separates transport protocols, business logic, persistence, and infrastructure orchestration. This separation of concerns ensures that the system remains modular and testable.

At the edge, the API gateway layer handles request termination, payload validation, and authentication extraction. Beneath it, the workflow service layer implements the core platform business rules. This layer is responsible for translating user intents—such as provisioning requests or schema generation—into actionable operations, enforcing resource-tier limits, validating credentials, and managing state transitions. 

Data persistence for the control plane relies on a dedicated meta-database for canonical state and an in-memory datastore for ephemeral data such as session tokens and transient workflow states. Finally, the infrastructure orchestration layer acts as the bridge between the control plane and the underlying container orchestrator, abstracting the complexities of interacting with database operators, networking rules, and secret management. 

By avoiding tight coupling between the application logic and the tenant databases (e.g., bypassing rigid Object-Relational Mappers for tenant queries), the system preserves the native execution semantics of the underlying engines, ensuring that complex queries and document aggregations are passed through faithfully.

\subsection{Polyglot Persistence Strategy}

The platform embraces polyglot persistence by intentionally supporting multiple database engines. Rather than forcing diverse application models into a single storage paradigm, the architecture offers engines tailored to specific data structures and access patterns.

\subsubsection*{Relational Engine Selection}

PostgreSQL was selected as the foundational relational engine for both the platform's internal meta-database and tenant workloads. For the control plane, strong ACID (Atomicity, Consistency, Isolation, Durability) guarantees, strict relational integrity, and robust transaction management are critical for maintaining the canonical state of users, projects, and billing tiers. 

For tenant workloads, PostgreSQL offers significant advantages over alternatives like MySQL. It provides comprehensive support for advanced SQL features, including complex window functions, common table expressions, and rich indexing strategies. Furthermore, its highly optimized JSONB capabilities allow developers to store and query semi-structured data efficiently without leaving the relational ecosystem. The maturity of its operator ecosystem in Kubernetes ensures that declarative provisioning, scaling, and high availability can be achieved reliably. Additionally, PostgreSQL's compatibility with automatic REST API generators enables rapid frontend development by exposing relational tables directly over HTTP.

\subsubsection*{Document Engine Selection}

MongoDB was integrated to serve as the document-oriented database engine. Many modern applications—particularly those in the prototyping phase or dealing with naturally nested, polymorphic data—benefit from schema flexibility. Forcing these models into normalized relational tables often introduces unnecessary friction and migration overhead.

MongoDB excels in these scenarios by providing highly expressive querying, aggregation, and indexing capabilities over deeply nested BSON documents. This structure maps perfectly to the JSON objects consumed by modern web and mobile clients, eliminating the impedance mismatch between the application layer and the persistence layer. Like PostgreSQL, MongoDB is supported by a mature Kubernetes operator ecosystem, allowing the platform to reuse the same declarative provisioning and namespace isolation patterns across both engines.

Ultimately, providing both engines ensures the platform is broadly applicable. Users are empowered to select the storage paradigm that best aligns with their application's domain logic rather than compromising their architecture to fit the database.

\subsection{Control Plane Data Model}

The canonical state of the platform is maintained in the control plane's meta-database. The schema is intentionally minimized; rather than duplicating tenant database topologies, the meta-database acts as a directory, while the source of truth for database topology remains with the Kubernetes operators.

The core Entity-Relationship model centers on two primary entities: \textbf{Users} and \textbf{Projects}. The Users entity stores authentication credentials, roles, and status flags. The Projects entity maintains a many-to-one relationship with Users (a user may own multiple projects). A Project record encapsulates the requested database engine type, the assigned resource tier, and the current lifecycle status (e.g., creating, running, failed). 

Crucially, the meta-database does not store raw connection strings or tenant database credentials. Instead, it relies on deterministic naming conventions and the Kubernetes Secrets API to dynamically resolve connection parameters at runtime, significantly reducing the security risk associated with centralized credential storage.

\subsection{Asynchronous Provisioning State Machine}

Infrastructure provisioning in a containerized environment can take several minutes as volumes are bound, pods are scheduled, and databases are bootstrapped. To prevent long-lived HTTP connections from blocking the API layer, the provisioning workflow is modeled as an asynchronous state machine.

When a user requests a new database, the system performs optimistic validation of the request payload and resource tier. If valid, the project is registered in the meta-database with a \textit{creating} state, immediately returning a stable identifier to the client. The API gateway then enqueues a provisioning task into an in-memory message broker (Redis), decoupling the request ingestion from its execution.

A decoupled background orchestration worker consumes these tasks and sequentially drives the infrastructure state: it creates a mathematically deterministic namespace for isolation, injects cryptographic secrets, and submits the declarative Custom Resources to the respective database operators. The worker then enters a polling loop, waiting for the operator to report readiness. Upon successful deployment, the project transitions to a \textit{running} state. If the orchestration process times out or encounters an unrecoverable failure, the infrastructure is rolled back, and the project transitions to a \textit{failed} state. This event-driven, eventual consistency model requires the client to poll the project status but ensures the control plane API remains highly responsive under heavy provisioning loads.

\subsection{Resource Tiering and Enforcement}

Tenant databases are strictly constrained by resource tiers. These tiers define the maximum allowable CPU cores, memory limits, and persistent storage capacity. During the provisioning state machine's execution, these limits are translated directly into Kubernetes resource quotas and persistent volume claims. 

To further mitigate ``noisy-neighbor'' problems and protect the control plane, the infrastructure leverages compute isolation via Kubernetes Node Pools. Control plane components, API gateways, and system operators are pinned to a dedicated System Node Pool. In contrast, tenant workloads are scheduled exclusively on a distinct Tenant Node Pool using node taints and tolerations. This physical segregation ensures that an unconstrained, compute-intensive query running on a tenant database cannot starve the cluster's critical management services of CPU or memory resources, enforcing constraints at both the orchestration and hardware levels.

\subsection{Data Plane Network Routing}

The platform is designed to support two distinct data access patterns: programmatic access via the REST API and direct access via standard database client tools. 

For direct relational database access, the system employs a dedicated Transport Layer Security (TLS) routing proxy. Instead of terminating the TLS connection—which would disrupt the database's native authentication protocols and channel-binding mechanisms—the proxy inspects the unencrypted Server Name Indication (SNI) extension in the initial TLS \texttt{ClientHello} packet. It extracts the unique project identifier from the SNI hostname and dynamically routes the TCP byte stream to the appropriate isolated namespace. This design ensures that encryption and authentication remain strictly end-to-end between the user's local client and the tenant database.

Document database routing follows a similar principle, utilizing ingress controllers configured for TCP TLS passthrough to direct traffic safely into the correct namespace.

\subsection{Dynamic Connection Pooling}

To manage connections to thousands of potential tenant databases efficiently, the backend employs a Just-In-Time (JIT) connection pooling strategy. Establishing database connections is computationally expensive. Therefore, the control plane caches connection pools in memory, keyed by the project identifier.

When a query is dispatched, the system attempts to acquire an active pool. The pool configuration is highly conservative, utilizing a minimal baseline connection count and a strict upper limit to prevent connection exhaustion at the database layer. Before a cached pool is returned, the system verifies its liveness and checks for connection parameter rotations. A background reclamation process periodically identifies and evicts pools that have remained idle, freeing resources on both the control plane and the tenant databases while ensuring low-latency access for active projects.

\subsection{AI Delegation and Query Validation}

The integration of artificial intelligence for schema generation and natural language query synthesis (Text-to-SQL) is treated as a delegated capability. The core system does not embed large language models directly; instead, it acts as a secure intermediary. The backend constructs the appropriate prompt context, dispatches it to external AI services, and streams the generated artifacts back to the client.

Crucially, AI-generated artifacts are treated as untrusted input. Generated Data Definition Language (DDL) is cached as a pending proposal and requires explicit user approval before execution. Similarly, generated SQL queries pass through an application-level query safety validator. This validator enforces security constraints, blocking high-risk operations such as schema truncation or unguarded deletion statements. While this is not a complete cryptographic sandbox, it provides a critical layer of defense against accidental or hallucinated destructive commands.

\subsection{Disaster Recovery and Continuous Archiving}

Data durability and disaster recovery are foundational to the platform's architecture. Instead of relying solely on periodic manual dumps, the system implements continuous Point-in-Time Recovery (PITR) mechanisms. For PostgreSQL workloads, the CloudNativePG operator is configured to continuously archive Write-Ahead Logs (WAL) to an external S3-compatible object storage bucket. Similarly, MongoDB instances offload scheduled snapshots to object storage. This decoupling of storage ensures that even in the event of catastrophic node failure or complete loss of the Kubernetes persistent volumes, tenant databases can be fully reconstructed up to the last committed transaction without impacting the cluster's local storage capacity.

\subsection{Streaming Export and Restore Pipelines}

In addition to continuous disaster recovery, the architecture optimizes manual data export and restore operations through streaming data pipelines rather than relying entirely on localized disk materialization. For export operations, the backend spawns the native database dumping utilities and pipes their standard output directly into the HTTP response stream. This approach ensures that the control plane's memory and storage are not overwhelmed when exporting gigabytes of data. Import operations function in reverse, streaming the uploaded payload directly into the restoration process. This streaming design is essential for maintaining a stateless, horizontally scalable API tier.
