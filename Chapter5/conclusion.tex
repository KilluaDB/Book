\section{Chapter Summary}

This chapter detailed the technical implementation of the DBaaS platform, bridging the gap between high-level architectural design (Chapter~\ref{chap:system_design}) and the underlying Kubernetes runtime. By utilizing Go for its concurrency model and Kubernetes client ecosystem, the backend separates the control-plane REST API from data-plane components such as tenant databases, PostgREST resources, and PGProxy. Delegating database lifecycle management to CloudNativePG and the MongoDB Community Operator keeps provisioning declarative while allowing the backend to focus on validation, metadata, status reconciliation, connection management, and query execution.

Authentication combines Argon2id password hashing, JWT access tokens, Redis-backed refresh-token rotation, and optional Google OAuth2. Administrative user management is gated by role-based middleware, and SQL execution remains centralized behind a validation layer that blocks multi-statement and high-risk statements before they reach tenant databases.

The integration of Flutter as the presentation layer abstracts this orchestration behind a responsive user interface, allowing users to provision, manage, and query relational and NoSQL databases without interacting directly with Kubernetes. Performance evaluation on the local k3d cluster measured provisioning latency, PGProxy routing overhead, and idle tenant memory footprint using reproducible benchmark procedures documented in this chapter.

The current deployment workflow uses containerized Go binaries (API and pgproxy), Kubernetes manifests with ClusterRole-scoped RBAC, and local k3d automation through \texttt{start.sh}. The same architecture can be hardened for production through managed metadata services, stricter network and CORS policies, registry-backed image delivery, multi-replica Deployments, and production-grade storage and secret management.
